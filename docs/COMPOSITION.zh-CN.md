# 把底层与其他组件组合

[English](COMPOSITION.md) · [首页](../README.zh-CN.md)

本库提供状态、带可见范围的记录和行动结果，接入的应用决定它们的含义并连接其他组件。
只保存状态、只发布记录、只保存意图与结果都能运行，不要求同时提供另外两类内容。
记录种类、参与者 ID、JSON 结构、业务规则和执行顺序由应用决定。
这些能力仍共用一个包和 SQLite 结构，并非分别安装或随意更换的存储引擎。

## 已实际运行的两条组合路径

| 组合 | 底层负责 | 外部组件负责 | 已测试范围 |
|---|---|---|---|
| [LangGraph](LANGGRAPH.md)＋本库 | 业务状态、可见记录、提交凭据 | 图执行、中断、图检查点 | 同步 `invoke`、人工恢复、节点重跑 |
| [LangChain Core 检索示例](../examples/langchain_retrieval.py)＋本库 | 原始记录、接收范围、历史 | 派生内存存储与 Runnable 管线 | 关键词查找、各参与者独立缓存、新提交后重建 |

两条路径均实际调用上游接口，使用确定性函数和虚构资料。
它们属于同一个 LangChain 生态，不能据此声称所有框架都兼容或模型理解更好。

## 运行检索组合示例

在当前源码目录的虚拟环境中执行：

```powershell
python -m pip install -r requirements/retrieval-test.txt
python -m examples.langchain_retrieval
python -B tools/verify.py --retrieval
```

这里安装 **langchain-core 1.6.11** 及其依赖，不要求安装 LangGraph 本身；
约束文件复用已有测试版本集合。不调用模型，不需要嵌入、向量库或 API key。
固定源码、MIT 许可证和实际依赖用途见[上游核查](UPSTREAM.md)。

`build_retriever(view)` 接收已经筛选的 `View`，不接收有全局权限的 Ledger 或状态快照。
它为这名参与者、这个读取版本新建 `InMemoryStore`，再组合两个 `RunnableLambda` 步骤：
先对记录正文进行忽略大小写的子串匹配，再返回参与者、读取版本、匹配记录及其 ID 和来源。
关键词匹配是示例策略，不是语义搜索，也不是核心接口。

示例里，操作员能检索公开和发给自己的操作资料，不能读到复核者私有记录或宿主状态。
新记录提交后，旧缓存仍停在原版本，重建后才能检索新资料。
测试另覆盖工作线程调用、修改返回值不污染缓存，以及外部缓存建立失败后从已提交记录重建。

先按接收范围筛选，再把内容交给外部存储；缓存按参与者和读取版本分开。
宿主决定提供哪份 View，参与者 ID 本身不承担身份认证。
记录保留历史，撤回或被修订的理解需要应用先决定如何处理，不能把全部旧记录直接当作当前结论。
核心提交与外部缓存没有共同事务；本例把缓存作为可重建的派生数据。

检索与理解交接示例属于 Unreleased 源码更新，现有 alpha 2 附件不含这些新增示例；
示例代码也不包含在安装后的核心包中。

## 复现组合能力与限制

```powershell
python -B tools/audit_composition.py
```

这个标准库脚本使用临时数据库运行 12 项检查。限制检查通过，表示成功复现了该限制，
不表示任意组合都已经支持。

| 边界 | 实际行为 | 接入时意味着什么 |
|---|---|---|
| 全局提交版本 | 即使状态不变，只新增一条记录也会让旧版本方案过期；更新不同字段同样冲突 | 重新读取并判断旧方案，不能直接替换版本号后提交 |
| 最近条数不是分页 | 同一提交有 5 条记录，`last=2` 只返回最新 2 条；直接推进到 `View.revision` 会跳过另外 3 条 | 完整消费增量时不加 `last`，处理完整结果后再推进版本 |
| 连接归属一个线程 | 把同一个 Ledger 交给工作线程会失败；工作线程自己连接同一个文件可以读取 | 在执行 SQLite 操作的位置管理连接；另建内存 Ledger 不会共享原数据 |
| 专用数据库结构 | 拒绝其他数据库，也拒绝在本库中添加应用表 | 使用独立文件；没有共用外部事务或可替换后端接口 |
| 严格 JSON、整值更新 | 外部对象需显式转换；嵌套更新会替换整个顶层值 | 宿主适配对象格式并计算完整更新结果 |
| 应用自定义元数据 | 先取最近几条再按项目筛选，可能漏掉更早的匹配内容 | 不截断地读取再筛选、有意识地使用种类，或分别建库 |
| 多个独立 Ledger | 各自有自己的版本 | 不提供跨库原子提交 |

另一次实际调用确认：现有 LangGraph 示例的同步节点持有调用者的 Ledger，
改成 `ainvoke` 时节点会在工作线程执行，并在测试环境触发 SQLite 的线程归属错误。
当前验证的是同步 `invoke`。异步适配需要自己的连接生命周期和测试，本例尚未提供。

## 值得继续改进的底层能力

可保证完整性的分批增量消费、明确的异步接入方式，以及更细的过期判断，都值得下一步评估。
记录游标必须覆盖同一版本中的多条记录；更细的冲突检查也必须保留对记录和状态的实际依赖。
这些是候选设计，尚未新增对应接口，也不意味着可以自动合并不同参与者的决定。
具体证据及限制见[验证记录](VALIDATION.md)。
